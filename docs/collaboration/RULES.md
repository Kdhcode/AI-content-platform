# 공통 협업 규칙

이 문서가 협업 규칙의 단일 원본이다. `CLAUDE.md`·`AGENTS.md`는 이 문서를 가리키기만 한다. 규칙을 바꿀 때는 이 문서만 고친다.

## 1. 역할

- **사용자:** 작업 범위·제품 정책 결정, 승인(아래 6절), `main` 병합, PR 생성·병합.
- **Claude Code:** 구현, 검증 실행, `TASK.md` 기록, 리뷰 지적의 직접 검증과 반영. 정책 판단이 필요한 것은 결정하지 않고 사용자에게 묻는다.
- **GPT(ChatGPT·Codex CLI):** 작업 지시 정리와 독립 리뷰. Codex CLI는 `tools/codex_review.py`가 읽기 전용으로 실행하며 코드를 고치지 않는다. 리뷰 의견은 근거를 확인한 뒤에만 반영한다(무조건 적용하지 않음).

## 2. 작업 시작 전 확인

1. `git fetch` 후 현재 브랜치·HEAD·upstream·원격과의 차이를 확인한다. 원격 이름을 확인하고 `origin`으로 가정하지 않는다.
2. 미커밋 변경과 다른 작업 트리(`git worktree list`)를 확인한다.
3. 관련 PR이 열려 있는지, 그 head·base·CI 상태를 확인한다.
4. `TASK.md` 상단 "현재 상태"와 최근 절을 읽는다. 다른 기기에서 push한 커밋이 현재 브랜치에 없는지 확인한다.
5. 예상과 다르면(브랜치·커밋·원격 상태) 먼저 원인을 확인하고, 덮어쓰지 않는다.

## 3. Git

- `main`에 직접 push하지 않는다. `main` 병합은 사용자가 요청할 때만 한다.
- 작업은 `claude/*` 브랜치에서 한다. 작업 브랜치는 사용자가 요청하기 전에는 지우지 않는다.
- 미커밋 변경을 보존한다. force push, `--all`·`--mirror` push, 임의 `stash`, `reset --hard`를 하지 않는다.
- 작은 단위로 커밋하고 이번 작업 파일만 포함한다. API 키·비밀번호·상세 로그·로컬 설정은 Git에 올리지 않는다.
- 같은 작업을 두 기기에서 동시에 하지 않는다. 기기를 바꾸기 전에 commit·push, 바꾼 뒤 fetch·pull.

## 4. 검증과 기록

- 변경 범위에 맞는 검증을 실행한다. 결과에는 실행 명령, 기준 커밋, 통과/실패/미실행을 적는다. 실행하지 못한 검증은 미실행으로 적고 이유를 남긴다.
- 검증 근거를 구분해 적는다: **직접 실행**(이번 작업에서 실행), **전달받은 보고**(다른 기기·다른 세션의 기록), **원격 조회**(GitHub API·`ls-remote` 등). 이전 커밋의 결과를 현재 커밋의 결과로 쓰지 않는다.
- 테스트 삭제, 검사 완화, 가짜 AI 결과로 통과시키지 않는다. 요약 사실성·이슈 분류 정확도는 사람이 정답을 정한 평가 세트로 검증한다. 두 모델의 의견 일치는 정확도의 근거가 아니다.
- `TASK.md` 상단 "현재 상태"는 **검증한 코드 커밋 SHA** 기준으로 갱신한다(브랜치, 그 SHA, 검증 결과 요약, 열린 PR, 다음 작업). 작업마다 아래에 절을 추가하고, 이전 절의 사실은 고치지 않고 정정이 필요하면 정정 표시를 남긴다.
- 수정 반복은 최대 3회. 해결하지 못한 문제는 기록하고 사용자에게 전달한다.

## 5. 리뷰 절차 (구현 커밋 뒤)

1. 구현을 커밋한다(리뷰는 커밋된 내용만 본다. 저장만 한 파일은 보지 않는다).
2. `python tools/codex_review.py --commit <sha>`(커밋 하나) 또는 `--range <기준 브랜치>`(브랜치 전체 diff)로 리뷰한다. 실제 호출 전에 `--dry-run`으로 보낼 입력(diff·전체 파일·문맥 문서)과 제한 설정을 확인할 수 있다. 실제 Codex 호출은 사용량이 들므로 사용자가 승인한 범위·횟수 안에서만 한다.
3. 출력된 결과 파일(`.local/collaboration/reviews/<sha 또는 range-...>.md`, Git 제외)을 읽는다.
4. 지적마다 "확인"인지 "가설"인지 직접 검증한다(코드 읽기, 재현, 테스트).
5. 확인된 것만 수정하고 관련 테스트를 실행한다. 가설이 재현되지 않으면 수정하지 않고 근거와 함께 보류로 적는다.
6. 정책·제품 판단이 필요한 지적은 수정하지 않고 사용자에게 질문으로 남긴다.
7. 수정 커밋이 의미 있게 바뀌었으면 다시 리뷰한다(승인 범위 안에서).
8. 남은 지적과 판단 근거(수정함·보류·질문)를 `TASK.md`에 기록한다.

## 6. 승인 범위

- 다음은 각각 사용자의 명시적 승인이 있어야 한다: `main` 병합·`main` push, 실제 사용하는 DB의 변경(마이그레이션 포함), 유료 API 호출(유료 AI, Codex 사용량 포함), 외부 발행(블로그 등), 실제 RSS 수집.
- "다음 작업 진행해줘" 같은 일반 지시는 위 항목을 승인한 것이 아니다.
- 승인은 지정한 범위·횟수·대상에만 적용된다. 그 작업이 끝나면 다시 승인을 받는다.
