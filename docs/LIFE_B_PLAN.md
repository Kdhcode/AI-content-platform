## 1. 구조 제안 (테이블 2개 + 기존 감사 로그)

판정 결과(자주 쌓이고 고치지 않음)와 관리자 제외(이슈마다 현재 상태 하나, 사람이 바꿈)는 수명과 변경 주체가 달라서 나눈다. 테이블을 하나로 합치면 재판정 행이 추가될 때 제외 상태를 복사해야 하고, 그러다 빠지면 제외가 풀린다(D5 위반).

### 1-1. `life_judgment` — 판정 이력 (추가만 함)

| 열 | 형식 | 내용 |
|---|---|---|
| `id` | BIGSERIAL PK | |
| `issue_id` | BIGINT NOT NULL FK → `issue` | 판정 대상 |
| `input_change_seq` | BIGINT NOT NULL CHECK (≥ 0) | 판정 입력을 만들 때 읽은 `issue.change_seq`(D3) |
| `life_related` | BOOLEAN NOT NULL | 생활 관련 여부 |
| `category` | VARCHAR(50) NULL | 지금은 자유 문자열(D8). `life_related = false`면 NULL 허용 |
| `relevance_score` | NUMERIC(4,3) NOT NULL CHECK (0 ≤ 값 ≤ 1) | D1. 소수 셋째 자리까지(0.91 → 0.910) |
| `reason` | TEXT NOT NULL | 판정 이유(길이 상한은 B2 스키마와 함께 정함) |
| `prompt_version` | TEXT NOT NULL | 예: `life-classifier.v1` |
| `model` | TEXT NULL | 사용 모델(사람이 직접 판정하는 경로가 생기면 NULL) |
| `source_job_id` | BIGINT NULL FK → `async_job`, **UNIQUE** | 이 판정을 만든 작업. 재시도 중복 방지(4절) |
| `judged_by` | TEXT NOT NULL | 요청한 관리자(작업의 `requested_by`) |
| `judged_at` | TIMESTAMPTZ NOT NULL DEFAULT now() | 결과를 저장한 시각 |

인덱스: `(issue_id, input_change_seq DESC, id DESC)` — 현재 판정 선택(2절)과 이슈별 이력 조회에 같이 씀.

행을 고치거나 지우지 않는다. 판정이 틀렸으면 재판정(새 행) 또는 관리자 제외(1-2)로 다룬다.

### 1-2. `life_exclusion` — 관리자 제외 (이슈당 현재 상태 하나)

| 열 | 형식 | 내용 |
|---|---|---|
| `issue_id` | BIGINT PK FK → `issue` | 이슈당 한 행 |
| `excluded` | BOOLEAN NOT NULL | 제외 여부. 다시 포함하면 행을 지우지 않고 `false`로 |
| `reason` | TEXT NULL | 제외 사유(제외할 때 필수로 할지는 7절 질문) |
| `updated_by` | TEXT NOT NULL | 마지막 처리자 |
| `updated_at` | TIMESTAMPTZ NOT NULL DEFAULT now() | 마지막 처리 시각 |

- 판정 행과 연결하지 않으므로 재판정이 몇 번 추가돼도 제외 상태는 그대로다(D5).
- 처리 이력(누가 언제 제외·복귀했는지)은 기존 `admin_audit_log`에 남긴다: `LIFE_EXCLUDE`, `LIFE_INCLUDE`(전후 상태·사유). 별도 이력 테이블은 만들지 않는다(콘텐츠 상태 동작과 같은 방식).

## 2. 현재 판정과 상태 계산

**현재 판정 선택 기준:** 이슈의 판정 행 중 `input_change_seq`가 가장 큰 것, 같으면 `id`가 가장 큰 것(나중에 저장된 것).

- 오래된 입력의 판정이 늦게 끝난 경우: 예를 들어 change_seq 3에서 시작한 판정 A가 change_seq 5에서 시작한 판정 B보다 늦게 저장돼도, 현재 판정은 B다. A는 이력으로만 남는다. 저장 시각(`judged_at`)이나 `id`만으로 고르면 오래된 입력이 새 입력을 덮는다.
- 같은 입력 시점으로 두 번 판정한 경우(관리자가 같은 이슈를 다시 요청): 나중에 저장된 쪽이 현재 판정이다.

**상태(조회 시 계산, 저장하지 않음):**

| 상태 | 조건 |
|---|---|
| 미판정 | 판정 행이 없음(D6) |
| 판정됨 | 현재 판정의 `input_change_seq` = `issue.change_seq` |
| 재판정 필요 | 현재 판정의 `input_change_seq` < `issue.change_seq`(D4) |
| 관리자 제외 | `life_exclusion.excluded = true` — 판정 상태와 별개의 표시. 제외돼도 판정·재판정 필요 여부는 그대로 계산해 보여 줌 |

후보 여부(`life_related`와 기준점수)는 D8 결정 전까지 계산하지 않는다. 생활 관련 여부·점수·카테고리를 그대로 보여 준다.

## 3. 원천 이슈가 바뀔 때 (`change_seq` 경로 확인, 2026-10-23 코드 읽기)

V7 트리거(`trg_issue_change_seq`, `trg_issue_article_change_seq`, `trg_issue_article_move_change_seq`)가 실제로 `change_seq`를 올리는 경로:

| 동작 | 코드 경로 | 오르는 이슈 | 기존 테스트 |
|---|---|---|---|
| 기사 이동 | `IssueManagementService.move` → `IssueRepository.repointArticle`(`UPDATE issue_article SET issue_id`) | 원래 이슈·옮겨 간 이슈 둘 다 | 옮겨 간 쪽만(`ContentOriginChangeIntegrationTest` 기사 합류) |
| 병합 | `merge` → 원본 기사마다 `repointArticle` + `markMerged`(`status = 'MERGED'`) | 원본(기사 이탈 + 상태 변경), 대상(기사 합류) | 원본 쪽만(`mergedAndExcludedOrigins…`) |
| 분리 | `split` → `issues.create`(새 이슈 `change_seq` 0) + 기사마다 `repointArticle` | 원래 이슈(기사 이탈), 새 이슈(기사 합류로 1 이상) | 원래 이슈 쪽만(`articleMembership…` 마지막 단계) |
| 제목·요약·분류·상태 수정 | `update` → `updateFields` | 해당 이슈(값이 실제로 바뀔 때만) | 있음 |
| 자동 집계 | `aggregates.refresh`가 AUTO 제목·요약을 바꿀 때 | 해당 이슈 | 간접 |

판정에 미치는 결과:
- 병합된 원본 이슈: 판정 행은 그대로 남는다(이력). 상태가 MERGED라 판정 대상 목록에서 빠지고, 병합 대상 이슈는 `change_seq`가 올라 **재판정 필요**가 된다. 원본의 판정을 대상 이슈로 옮기지 않는다.
- 분리로 생긴 새 이슈: 판정 행이 없으므로 **미판정**. 원래 이슈는 기사 이탈로 **재판정 필요**.
- **B1 구현 때 추가할 테스트:** 병합 대상 이슈의 `change_seq` 증가, 분리로 생긴 새 이슈의 미판정 상태, 이동한 기사가 떠난 이슈의 증가(지금 테스트는 받는 쪽만 확인).

참고: `change_seq`는 이슈 상태 변경(예: ACTIVE → CLOSED)에도 오른다. 상태만 바뀐 경우까지 재판정 필요로 볼지는 7절 질문.

## 4. 재시도 중복과 재판정 구분

| 경우 | 처리 |
|---|---|
| 같은 작업의 재시도(작업자 중단·타임아웃 뒤 같은 `async_job`을 다시 실행) | `source_job_id` UNIQUE + `INSERT … ON CONFLICT (source_job_id) DO NOTHING`. 결과 저장과 작업 성공 표시를 한 트랜잭션으로 처리해 판정 행이 하나만 남음 |
| 관리자의 재판정 요청 | 새 `async_job`을 만들므로 새 판정 행(D2) |
| 같은 요청 화면에서 중복 클릭 | B3 API에서 `Idempotency-Key`(콘텐츠 생성과 같은 방식)로 같은 작업을 돌려줌. 이 때문에 판정 행이 두 번 생기지 않음 |
| AI 응답 실패·스키마 위반 | 판정 행을 만들지 않음. 실패는 `async_job`·`ai_log`에 남고 이슈는 이전 상태(미판정 또는 이전 판정) 그대로 |

입력 시점(`input_change_seq`)은 작업을 요청한 때가 아니라 **작업자가 판정 입력(이슈 사실·기사 목록)을 읽는 같은 트랜잭션 안에서** 읽는다. 요청과 실행 사이에 이슈가 바뀌어도 실제로 본 입력과 맞는 번호가 남는다.

## 5. B3 이후가 기대는 동작 (참고, 이번 범위 아님)

- 판정 요청: 관리자가 이슈를 골라 요청(D7). 이슈마다 `async_job` 하나. MERGED 이슈는 거부(병합 대상에서 요청하라는 안내). 제외된 이슈 요청을 막을지는 7절 질문.
- 조회: 이슈별 현재 판정·상태(2절), 이력(최신순), 제외 여부.
- NEWS와 LIFE 동시 유지: 판정은 이슈의 부가 정보다. 판정 결과가 이슈 상태·이슈 요약·NEWS 콘텐츠 생성을 바꾸지 않는다.
- 공개 API·뉴스룸에는 판정 정보를 노출하지 않는다.

## 6. B1 구현 범위와 완료 기준 (다음 작업)

- 범위: V8(1절 두 테이블), 저장소(판정 저장·현재 판정·상태 계산·이력, 제외 설정·해제 + 감사 기록), 서버 검증(점수 0~1, 필수값), 테스트. AI 호출·작업 실행·API·화면 제외.
- 완료 기준:
  - V8이 빈 DB와 `aicontent_main` 복사본에 적용되고 기존 테이블 데이터가 그대로(V7 리허설과 같은 방식)
  - 테스트: 점수 범위(0, 1 통과 / 음수·1 초과 거부), 미판정 → 판정됨 → 이슈 변경 후 재판정 필요 → 재판정으로 판정됨, 오래된 입력의 늦은 판정이 현재 판정을 바꾸지 않음, 같은 작업 재시도에 행 하나, 제외가 재판정 뒤에도 유지, 3절 추가 테스트(병합 대상·분리 새 이슈·이동 원래 이슈)
  - 기존 테스트 전체 통과
- 실제 `aicontent_main`에 V8 적용은 별도 승인(적용 전 백업·복원 확인·리허설).

## 7. 결정이 필요한 것 (임의로 정하지 않음)

1. **상태만 바뀐 경우의 재판정 필요:** `change_seq`는 상태 변경(ACTIVE ↔ CLOSED 등)에도 오른다. 판정 입력(사실·기사)이 그대로인 상태 변경까지 재판정 필요로 볼지, 판정용 번호를 따로 둘지.
2. **제외 사유 필수 여부와 권한:** 제외할 때 사유를 필수로 할지, OPERATOR도 제외·복귀할 수 있는지(콘텐츠 상태 동작은 OPERATOR+).
3. **제외된 이슈의 판정 요청:** 막을지, 허용하고 표시만 할지.
4. **판정 입력 기록:** 판정에 쓴 입력(사실 목록·기사 id)을 판정 행에 남길지(평가 재현에 유리, 저장량 증가), `async_job.payload`·`ai_log`로 충분한지.
5. **CLOSED 이슈:** 판정 대상에 넣을지(콘텐츠 생성은 ACTIVE·CLOSED 허용).
6. (D8) 카테고리 목록·후보 기준점수 — B4 평가 후.
