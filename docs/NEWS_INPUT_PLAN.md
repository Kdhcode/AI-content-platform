## 3-1. 이용 범위 확인 항목 (10-25 보완)

"허용/금지" 하나로 보지 않고 아래 네 항목을 **소스마다 따로** 확인한다. 한 항목이 허용됐다고 다른 항목까지 허용된 것으로 보지 않는다. 각 칸의 값은 `미확인`(기본) / `허용`(근거 URL·확인 날짜·확인자 필수, 계약이면 계약 근거) / `금지` / `조건부`(조건을 적음).

| 항목 | 이 프로젝트에서 하는 일 | 확인할 것 |
|---|---|---|
| ① 수집·저장 | 피드(또는 원문·API)를 받아 `news_article`에 본문을 저장 | 자동 수집 허용 여부, 저장 가능 범위(전문/일부/메타데이터만), 보관 기간과 삭제 의무(계약 종료·기사 삭제·정정 시) |
| ② 외부 AI 전달·분석 | 본문을 OpenAI API로 보내 분석·임베딩·분류(3-2절) | 제3자(외부 AI 서비스)에 보내는 것 자체의 허용 여부. "AI 학습 금지" 문구가 분석 API 사용까지 막는지는 문구만으로 정하지 않는다(학습과 분석은 다르지만, 분석이라고 해서 자동으로 허용되는 것도 아님) |
| ③ 요약·가공 | AI 요약·핵심 사실·이슈 요약, NEWS·LIFE 초안 작성 | 요약·재구성·2차 저작물 작성 허용 여부, 원문 왜곡·개작 금지 조건 |
| ④ 공개·상업 이용 | 공개 뉴스룸·블로그 등에 결과를 게시, 향후 수익화 | 공개 게시 허용 범위(제목·링크만 / 요약 / 인용 길이), 상업 이용 여부 |

- 함께 기록: **출처 표시** 요구(표기 문구·위치), **보관·삭제 조건**. 확인되지 않으면 `미확인`으로 둔다.
- 현재 확인된 범위(3절·후보 문서 기준): 6개 언론사 RSS 모두 ①~④ 중 어느 항목도 이 프로젝트 용도로 `허용`이 확인되지 않았다. 안내 문구가 있는 곳은 대체로 개인적·비상업적 구독으로 한정한다.
- **원문 확보에 실패해 RSS 본문으로 계속하는 경우에도 RSS 본문의 ①~④ 확인이 필요하다.** RSS로 되돌아간다고 이용 범위 문제가 사라지지 않는다(6절).
- AI 제공자의 처리 조건(3-2절)은 이 표와 **별개**다. 자료 제공자가 ②를 허용해도 AI 제공자 조건을 따로 확인하고, AI 제공자가 학습에 쓰지 않는다고 해서 자료 제공자의 허락이 생기지 않는다.

## 3-2. AI 제공자의 데이터 처리 조건 (10-25 확인, 자료 제공자 허락과 별개)

**저장소에서 실제 쓰는 방식(코드로 확인):** 공급자는 `app.ai.provider`(`none | stub | openai`, 기본 `none`). `openai`일 때 OpenAI **API**를 직접 호출한다 — 분석은 `POST {base-url}/chat/completions`(`OpenAiClient`, 기본 모델 `gpt-4o-mini`, `response_format=json_object`), 임베딩은 `POST {base-url}/embeddings`(`OpenAiEmbeddingClient`, 기본 `text-embedding-3-small`). 기본 base-url은 `https://api.openai.com/v1`. 요청 본문에 `store` 값은 넣지 않는다. Responses·Assistants·Files·Batch API는 쓰지 않는다. ChatGPT(웹·앱 일반 서비스)는 이 흐름에 쓰이지 않으므로 **ChatGPT 이용 조건은 여기에 적용하지 않고 조사하지 않았다.**

| 항목 | 공식 근거의 내용(요지) | 근거(확인 2026-10-25) |
|---|---|---|
| 학습 사용 | API로 보낸 데이터는 2023-03-01부터 모델 학습·개선에 쓰지 않음(명시적으로 opt-in한 경우 제외). 엔드포인트 표에서 `/v1/chat/completions`·`/v1/embeddings` 모두 "Data used for training: No" | https://platform.openai.com/docs/guides/your-data (현재 https://developers.openai.com/api/docs/guides/your-data 로 이동) |
| 계약상 사용 범위 | OpenAI는 서비스 제공·법령 준수·정책 집행·남용 방지에 필요한 경우에만 고객 콘텐츠를 사용하고, 고객이 명시적으로 동의하지 않으면 서비스 개발·개선에 쓰지 않음(4.2) | https://openai.com/policies/services-agreement/ (OpenAI 서비스 계약, 효력 발생일 2026-01-01). API·기업용 서비스에 적용되고 개인용 서비스에는 적용되지 않는다고 명시 |

| 애플리케이션 상태 보관 | `/v1/chat/completions`·`/v1/embeddings`: 기본 "None". 예외(chat completions): `store=true`로 저장하는 경우, 프롬프트 캐시(GPU 로컬, 최대 24시간), 오디오 출력(1시간), 이미지·파일 입력의 CSAM 검사 시 보관 | your-data 문서. `store` 파라미터 설명은 https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create (기본값은 이 페이지에서 확인하지 못함 → **미확인**. 이 프로젝트는 값을 보내지 않음) |
| 보관 축소 | Zero Data Retention·Modified Abuse Monitoring은 사전 승인과 추가 요건이 필요(영업팀 문의) | your-data 문서. 이 프로젝트 계정의 적용 여부: **미확인** |
| 삭제 | 계약 해지 시 30일 이내 고객 콘텐츠 삭제(법적 보관 의무·서면 합의·남용 콘텐츠 예외) | 서비스 계약 11.3 |
| 입력 권리 | 고객은 입력에 필요한 권리·라이선스·허가를 보유함을 진술·보증(4.3), 제3자 권리를 침해하는 사용 금지(3.3) | 서비스 계약 |

- 따라서 **AI 제공자 조건으로는 "학습에 쓰이지 않는다"까지만 확인**된다. 기사 본문을 보낼 권리가 있는지는 자료 제공자의 허락(3-1절 ②) 문제이고, 서비스 계약 4.3에 따라 그 책임은 이 프로젝트(고객)에 있다.
- 미확인: 사용자 계정이 위 서비스 계약에 동의한 조직 계정인지, 계정 데이터 공유 설정(opt-in) 상태, 우리 요청이 데이터 상주(region) 설정을 쓰는지(기본 base-url은 리전 지정 없음).
- 공급자·엔드포인트·`store` 사용을 바꾸면 이 절을 다시 확인한다(예: Responses API는 기본 30일 애플리케이션 상태 보관 — 같은 문서).

## 5. 자료 부족 표시 (설계)

**10-25 보완 — 첫 단계는 "충분"을 판정하지 않는다.** 처음 설계(아래 신호표와 "충분/부족/판정 불가" 세 단계)는 글자 수·잘림 표시 같은 신호로 "충분"까지 정하게 되어 있었다. 신호가 없다는 것은 자료가 충분하다는 증거가 아니므로(예: 뉴시스처럼 길어도 전문인지 모르고, 표시 없이 잘린 본문도 있음), 첫 단계는 **관찰 가능한 상태와 그 이유만** 표시한다.

| 상태(첫 단계) | 뜻 | 이유로 함께 표시할 것 |
|---|---|---|
| `발췌 의심` | 아래 신호 중 하나 이상이 관찰됨 | 관찰된 신호 이름과 위치(예: "끝이 `...`", "전체 내용 링크 문구", "제목 반복", "안내 문구 제거 후 N자") |
| `본문 없음` | 정리 후 본문이 비었음 | 원래 길이, 제거된 안내 문구 |
| `별도 신호 없음` | 계산한 신호가 하나도 관찰되지 않음 | 계산한 신호 목록과 계산 규칙 버전. **"충분"이라는 뜻이 아니다** — 화면 문구도 "충분"·"정상"으로 쓰지 않는다 |
| `판정 실패` | 계산 중 오류, 입력 형식 이상 등으로 상태를 정하지 못함 | 실패 사유 |

- "충분/부족" 판정은 사람이 정답을 정한 평가 사례로 기준을 세운 뒤의 일이다(7절 6번). 그 전에는 위 네 상태만 쓴다.
- 핵심 정보 유무(사실 수·날짜·수치·개체)는 분석 결과가 있어야 계산되므로 첫 단계에서 제외하고, 나중에 별도 신호로 붙일지 정한다.
- **조회 시 계산을 우선 검토한다.** 신호는 저장된 `analysis_text`·제목만으로 외부 호출 없이 계산되므로, 관리자 API가 응답할 때 순수 함수로 계산하면 마이그레이션·재계산 배치·실제 DB 변경이 필요 없고, 규칙을 바꿔도 즉시 반영된다. 목록 화면 성능이나 상태로 필터·집계가 필요해지면 그때 저장(V8)을 검토한다. **이번에는 구현하지 않는다.**

## 6. 원문 확보를 붙일 때의 처리 원칙 (설계만)

**허용 판단이 먼저다.** 원문 확보 경로는 각 사의 이용 조건이나 계약으로 허용이 확인된 소스에만 켠다. 소스 설정에 허용 상태를 둔다: `미확인`(기본, 원문 확보 안 함) / `허용`(근거 URL·확인 날짜·확인자 필수) / `금지`. **10-25 보완:** 허용 상태는 하나가 아니라 3-1절의 네 항목(① 수집·저장 ② 외부 AI 전달·분석 ③ 요약·가공 ④ 공개·상업 이용)별로 둔다. 원문 확보는 ①이, 분석 작업은 ②가 `허용`일 때만 켠다.

- 확보 실패(네트워크·HTTP 오류·로그인/유료 안내 페이지·형식 변경): 원문 없이 RSS 본문으로 계속하고 "원문 확보 실패(사유)"로 표시. 재시도 횟수 제한. 로그인·유료벽은 우회하지 않고 실패로 기록. **RSS 본문으로 계속하는 것도 RSS 본문의 이용 범위(3-1절)가 확인된 경우에만 해당한다** — RSS 쪽 ②가 `미확인`이면 RSS 본문으로도 분석하지 않는 것이 이 원칙과 맞다(현재 운영 중인 RSS 분석을 멈출지는 7절 1번 결정)
- 허용 여부 불명확: 시도하지 않음(`미확인`), 자료 부족 표시만
- **출처 추적(원문을 붙이든 안 붙이든):** 본문마다 출처 종류(RSS 본문 / 원문 / 계약 API), 받은 URL(피드 URL 또는 기사 URL), 받은 시각, 받은 방식(어댑터·버전), 허용 근거 상태를 함께 저장. RSS 본문과 원문을 한 열에 덮어쓰지 않고 따로 둔다

## 7. 결정이 필요한 것 (정책 질문 — 임의로 정하지 않음)

1. **분석 사용 범위:** RSS 본문을 AI 분석 입력으로 쓰는 것이 각 사의 "개인적·비상업적 이용"에 해당하는지. 특히 SBS의 "AI학습 이용 금지" 문구를 분석 입력(학습 아님)에 어떻게 적용할지. 확인 전까지 해당 소스를 계속 쓸지. 10-25 보완: 3-1절 네 항목별로 정하고, 각 사 문의로 확인할지 결정. 연합뉴스는 저작권규약에 계약 사용자도 허가된 목적 외 AI 서비스 사용 불가 조항이 있다([NEWS_SOURCE_OPTIONS.md](NEWS_SOURCE_OPTIONS.md) 2절)
2. **저장 범위:** 원문을 확보한다면 전문을 저장할지, 분석 결과만 남길지
3. **보존 기간:** 수집 본문(RSS·원문)을 얼마나 보관할지, 이슈가 닫힌 뒤 지울지
4. **공개 표시:** 공개 뉴스룸에 어떤 텍스트를 보여 줄지(지금은 AI 요약 + 기사 링크). 원문 문장 인용 여부와 길이
5. **소스 구성:** 발췌형 피드(연합뉴스·경향·동아·BBC)를 유지할지, 본문이 긴 피드를 우선할지, 계약형 경로(연합뉴스 유료 협의, 언론사 공동 데이터 서비스 등)를 검토할지. 10-25: 후보 3개(통신사 제휴·빅카인즈·공공기관 보도자료) 비교는 [NEWS_SOURCE_OPTIONS.md](NEWS_SOURCE_OPTIONS.md)
6. **자료 부족 기준값:** 5절 신호의 기준값과 "부족"일 때 콘텐츠 작성(AI 초안)을 막을지, 경고만 할지. 10-25: 기준이 정해지기 전에는 5절의 네 관찰 상태만 표시하고 "충분/부족"은 판정하지 않는다

## 8. 자료가 부족할 때 AI가 보충하지 않게 하는 방법

- 현재 분석 프롬프트(v2 시스템 1·2번)는 "명시된 내용만", "본문이 짧으면 제목에서 확인되는 사실만 + confidence ≤ 0.5"를 지시한다. 다만 지켰는지 코드로 확인하지 않는다
- 설계: ① 자료 부족 판정을 분석·초안 생성 입력에 함께 넣고 "부족한 항목은 비워 두고 '확인 필요'로 표시"를 지시 ② 출력 사실마다 근거 문장 위치(입력 안의 문장 번호)를 요구하고 코드로 존재 여부 확인 ③ 입력에 없는 숫자·고유명사가 출력에 나오면 검수 대기로 보냄(코드로 대조) ④ 부족한 이슈의 NEWS·LIFE 초안은 섹션을 채우지 않고 "근거 부족" 안내만(수동 생성은 이미 빈 본문)
- 효과는 사람이 정답을 정한 평가 세트로 확인한다(기존 원칙)

## 9. 별도 후속 과제 (이번 범위 아님)

- **이슈 요약 갱신:** 지금은 처음 채운 요약이 유지된다. 기사가 합류할 때 갱신하는 방법(여러 기사 재요약·대표 기사 선택 등)은 따로 설계한다. 가장 긴 기사 요약으로 바꾸는 방식이 정답인지는 정하지 않았다(긴 요약이 정보가 많다는 보장이 없고, 발췌형 피드 간 비교가 불공정). **관리자가 직접 고친 요약(`summary_source = MANUAL`)은 어떤 방식이든 덮어쓰지 않는다**
- **공개 핵심 사실 표시:** 관리자에게만 보이는 핵심 사실을 공개할지, AI 추출 사실임을 어떻게 표시할지
- HTML 엔티티 미변환(`&apos;` 등) 수정 — 작은 결함, 별도 작업

## 10. 다음 구현 작업 추천: "기사 자료 상태 표시"(원문 확보 없이)

- **해결할 문제:** 어떤 기사·이슈가 발췌만으로 만들어졌는지 지금은 알 수 없어, 관리자가 근거가 얕은 이슈로 콘텐츠를 만들거나 AI 결과를 그대로 믿기 쉽다
- **달라지는 점:** 관리자 기사·이슈 화면에 기사별 "자료 상태(충분/부족/판정 불가)"와 이유(잘림 표시, 전체 내용 링크 문구, 제목 반복, 실질 길이)가 보인다. 이슈에는 소속 기사 중 부족 비율
- **포함:** 5절 신호 중 분석 전 계산 가능한 것(잘림 표시·전체 내용 문구·제목 반복·실질 길이)을 계산하는 순수 함수 + 저장(V8 또는 조회 시 계산 — 결정 필요) + 관리자 API 응답 필드 + 화면 표시 + 기존 기사 재계산(외부 호출 없음)
- **제외:** 원문 확보, 피드 변경, 분석 프롬프트 변경, 공개 화면, 기준값 확정(초기값은 제안값으로 두고 표시만), 이슈 요약 갱신
- **데이터·API·화면 영향:** `news_article`에 열 추가 또는 계산 전용(결정), 관리자 기사·이슈 응답에 필드 추가, 공개 API 변화 없음

- **AI 초안 생성(C 묶음)과의 관계:** 자료 상태는 초안 생성 전 "근거 부족" 경고·차단의 입력이 된다(7절 6번). C 묶음 계획은 바꾸지 않는다
