# 수집 자료 보강 설계 (NEWS 입력)

2026-10-23 작성. **조사와 설계만 했고 수집 기능은 구현하지 않았다.** 근거: 코드 읽기, `aicontent_main`(기사 35건)·`aicontent`(494건) 읽기 전용 조회, 각 사 공개 안내 페이지 조회. 새 뉴스 수집·기사 본문 수집·유료 AI 호출 없음.

목표: NEWS·LIFE 콘텐츠를 쓸 때 충분한 근거를 확보하는 방법을 정한다. 이용 조건이 확인되지 않은 자료를 "허용"으로 보지 않는다.

## 1. 현재 흐름과 정보가 줄어드는 지점

| 단계 | 코드 | 하는 일 | 정보 손실 |
|---|---|---|---|
| 수집 | `RssNewsSourceAdapter` | 피드 XML만 받음. 항목마다 제목·링크·언론사·작성자·분류·발행 시각과 본문 하나(`content:encoded` → `content` → `description` → `summary` 중 처음 값, HTML 태그만 제거)를 `news_article.analysis_text`에 저장 | **기사 링크의 원문은 가져오지 않음.** 피드가 주는 만큼만 남음. HTML 엔티티는 풀지 않음(예: 연합뉴스 `&apos;`가 그대로 저장) |
| 분석 입력 | `ArticleAnalysisService.promptVariables`, `AnalysisInputCleaner` | 제목·언론사·발행 시각·소스 분류 + 본문(이용 안내·링크 문구·이메일 제거 후 8,000자에서 자름) | 현재 데이터 최장 2,201자 → **자른 기사 없음** |
| 기사 분석 | `article-analysis/v2` | 요약 2~3문장, 핵심 사실 1~10개, 개체 ≤30 | 긴 기사도 같은 상한(2,201자 → 요약 134자·사실 10개) |
| 이슈 집계 | `IssueAggregateService.refresh`, `IssueContentMerger` | 핵심 사실 합쳐 ≤15개, 개체 ≤20개. 이슈 요약은 `fillAutoSummaryIfEmpty`로 **비어 있을 때 한 번만** 채움 | 처음 분류된 기사 요약이 굳음(#5: 3건 중 57자짜리 요약이 남음) |
| 공개 표시 | `PublicNewsController`, `news/[id]/page.tsx` | 이슈 제목·요약·분류와 기사 제목·링크 | 핵심 사실·개체는 공개 응답·화면에 없음(관리자 화면에만) |

## 4. RSS만으로 충분한 자료와 추가 확보가 필요한 자료

| 용도 | RSS만으로 | 근거 |
|---|---|---|
| 같은 사건 묶기(임베딩·분류) | 대체로 가능 | 제목 + 1~2문장으로도 사건 식별 정보(누가·무엇)가 들어감. 현재 이슈 분류가 이 입력으로 동작 중 |
| 관리자 검수용 이슈 요약 | 소스에 따라 부족 | 발췌형 피드는 요약이 제목 반복 수준(#3) |

## 5. 자료 부족 표시 (설계)

글자 수 하나로 판정하지 않는다. 기사마다 아래 신호를 계산해 저장하고(판정 근거 포함), 결과는 "충분/부족/판정 불가" 세 단계로 둔다. 기준값은 평가 사례를 보고 정한다(7절).

| 신호 | 판정 방법(코드로 계산) | 표본에서의 예 |
|---|---|---|
| 잘림 표시 | 본문 끝이 `...`·`…`·`···`·`⋯` | 연합뉴스 3건, 경향 5건 |
| 표시 없는 잘림 | 피드별로 본문 길이가 같은 값 부근에 몰리고 끝이 문장 부호로 끝나지 않음 | 동아 2건(500자 부근) |
| "전체 내용" 링크 문구 | `전체 내용 확인` 같은 원문 안내 문구 | SBS 10건 |
| 제목 반복 | 정규화한 본문이 제목과 같거나 제목을 거의 그대로 포함 | 연합뉴스 1건 |
| 실질 본문 길이 | 이용 안내·링크 문구·머리글(기자명·지역)·이메일을 뺀 길이 | SBS는 안내 문구를 빼면 250자 이상 짧아짐 |
| 핵심 정보 유무 | 분석 결과의 사실 수·날짜·수치·인물/기관 개체 유무(분석 후 계산) | 짧은 본문은 사실이 제목 재진술 위주 |

- 판정 불가: 본문이 비었거나 분석 실패.
- 신호와 판정은 관리자 화면에 보이고(이슈·콘텐츠 작성 화면에서 "근거 부족" 표시), 공개 화면에는 쓰지 않는다.

## 6. 원문 확보를 붙일 때의 처리 원칙 (설계만)

**허용 판단이 먼저다.** 원문 확보 경로는 각 사의 이용 조건이나 계약으로 허용이 확인된 소스에만 켠다. 소스 설정에 허용 상태를 둔다: `미확인`(기본, 원문 확보 안 함) / `허용`(근거 URL·확인 날짜·확인자 필수) / `금지`.

- 확보 실패(네트워크·HTTP 오류·로그인/유료 안내 페이지·형식 변경): 원문 없이 RSS 본문으로 계속하고 "원문 확보 실패(사유)"로 표시. 재시도 횟수 제한. 로그인·유료벽은 우회하지 않고 실패로 기록
- 허용 여부 불명확: 시도하지 않음(`미확인`), 자료 부족 표시만
- **출처 추적(원문을 붙이든 안 붙이든):** 본문마다 출처 종류(RSS 본문 / 원문 / 계약 API), 받은 URL(피드 URL 또는 기사 URL), 받은 시각, 받은 방식(어댑터·버전), 허용 근거 상태를 함께 저장. RSS 본문과 원문을 한 열에 덮어쓰지 않고 따로 둔다

## 7. 결정이 필요한 것 (정책 질문 — 임의로 정하지 않음)

1. **분석 사용 범위:** RSS 본문을 AI 분석 입력으로 쓰는 것이 각 사의 "개인적·비상업적 이용"에 해당하는지. 특히 SBS의 "AI학습 이용 금지" 문구를 분석 입력(학습 아님)에 어떻게 적용할지. 확인 전까지 해당 소스를 계속 쓸지
2. **저장 범위:** 원문을 확보한다면 전문을 저장할지, 분석 결과만 남길지
3. **보존 기간:** 수집 본문(RSS·원문)을 얼마나 보관할지, 이슈가 닫힌 뒤 지울지
4. **공개 표시:** 공개 뉴스룸에 어떤 텍스트를 보여 줄지(지금은 AI 요약 + 기사 링크). 원문 문장 인용 여부와 길이
5. **소스 구성:** 발췌형 피드(연합뉴스·경향·동아·BBC)를 유지할지, 본문이 긴 피드를 우선할지, 계약형 경로(연합뉴스 유료 협의, 언론사 공동 데이터 서비스 등)를 검토할지
6. **자료 부족 기준값:** 5절 신호의 기준값과 "부족"일 때 콘텐츠 작성(AI 초안)을 막을지, 경고만 할지

## 8. 자료가 부족할 때 AI가 보충하지 않게 하는 방법

- 현재 분석 프롬프트(v2 시스템 1·2번)는 "명시된 내용만", "본문이 짧으면 제목에서 확인되는 사실만 + confidence ≤ 0.5"를 지시한다. 다만 지켰는지 코드로 확인하지 않는다
- 설계: ① 자료 부족 판정을 분석·초안 생성 입력에 함께 넣고 "부족한 항목은 비워 두고 '확인 필요'로 표시"를 지시 ② 출력 사실마다 근거 문장 위치(입력 안의 문장 번호)를 요구하고 코드로 존재 여부 확인 ③ 입력에 없는 숫자·고유명사가 출력에 나오면 검수 대기로 보냄(코드로 대조) ④ 부족한 이슈의 NEWS·LIFE 초안은 섹션을 채우지 않고 "근거 부족" 안내만(수동 생성은 이미 빈 본문)
- 효과는 사람이 정답을 정한 평가 세트로 확인한다(기존 원칙)

## 9. 별도 후속 과제 (이번 범위 아님)

- **이슈 요약 갱신:** 지금은 처음 채운 요약이 유지된다. 기사가 합류할 때 갱신하는 방법(여러 기사 재요약·대표 기사 선택 등)은 따로 설계한다. 가장 긴 기사 요약으로 바꾸는 방식이 정답인지는 정하지 않았다(긴 요약이 정보가 많다는 보장이 없고, 발췌형 피드 간 비교가 불공정). **관리자가 직접 고친 요약(`summary_source = MANUAL`)은 어떤 방식이든 덮어쓰지 않는다**
- **공개 핵심 사실 표시:** 관리자에게만 보이는 핵심 사실을 공개할지, AI 추출 사실임을 어떻게 표시할지
- HTML 엔티티 미변환(`&apos;` 등) 수정 — 작은 결함, 별도 작업

## 10. 다음 구현 작업 추천: "기사 자료 상태 표시"(원문 확보 없이)

- **해결할 문제:** 어떤 기사·이슈가 발췌만으로 만들어졌는지 지금은 알 수 없어, 관리자가 근거가 얕은 이슈로 콘텐츠를 만들거나 AI 결과를 그대로 믿기 쉽다
- **달라지는 점:** 관리자 기사·이슈 화면에 기사별 "자료 상태(충분/부족/판정 불가)"와 이유(잘림 표시, 전체 내용 링크 문구, 제목 반복, 실질 길이)가 보인다. 이슈에는 소속 기사 중 부족 비율
- **포함:** 5절 신호 중 분석 전 계산 가능한 것(잘림 표시·전체 내용 문구·제목 반복·실질 길이)을 계산하는 순수 함수 + 저장(V8 또는 조회 시 계산 — 결정 필요) + 관리자 API 응답 필드 + 화면 표시 + 기존 기사 재계산(외부 호출 없음)
- **제외:** 원문 확보, 피드 변경, 분석 프롬프트 변경, 공개 화면, 기준값 확정(초기값은 제안값으로 두고 표시만), 이슈 요약 갱신
- **데이터·API·화면 영향:** `news_article`에 열 추가 또는 계산 전용(결정), 관리자 기사·이슈 응답에 필드 추가, 공개 API 변화 없음
- **테스트·완료 기준:** 표본 패턴별 단위 테스트(연합뉴스 "...", 경향 "···", 동아 표시 없는 잘림, SBS 안내 문구, 제목 반복, 뉴시스 긴 본문), 기존 기사 재계산이 다른 열을 바꾸지 않음, 공개 응답에 필드 없음, 기존 테스트 전체 통과. 실제 DB 적용은 별도 승인
- **결정할 것:** 저장(마이그레이션) vs 조회 시 계산, 초기 기준값, "부족" 표시를 콘텐츠 만들기 화면에도 띄울지
- **LIFE B1과의 관계:** 판정 입력이 발췌뿐이면 생활 관련 판단도 얕다. B1 설계(`LIFE_B_PLAN.md`)는 바꾸지 않되, 판정 행에 입력의 자료 상태를 함께 남길지(7절 4번 "판정 입력 기록"과 연결)를 B1 결정 때 같이 보면 된다
- **AI 초안 생성(C 묶음)과의 관계:** 자료 상태는 초안 생성 전 "근거 부족" 경고·차단의 입력이 된다(7절 6번). C 묶음 계획은 바꾸지 않는다
