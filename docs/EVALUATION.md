# AI 평가 세트와 지표

## 목적
프롬프트·임계값·모델을 바꿀 때 "더 나아졌는가"를 같은 자로 재기 위한 고정 평가 세트입니다. 품질 합격선은 **정하지 않았습니다**(실제 공급자 기준선을 먼저 측정해야 함 → OPEN_ITEMS #4).

## 데이터: `backend/src/test/resources/eval/issue-eval-v1.json`
- 27건, 사건 그룹 10개 + 묶음 기사 2건. **모두 가상(fictional) 데이터**(가상시, 허구군, 예시전자, 샘플은행, 테스트대학교 등). 실제 뉴스·실존 인물/기관과 무관합니다.
- 필드: `id, publisher, publishedAt, title, summary, keyFacts[], entities[], eventGroup(정답 라벨), multiEvent, ambiguous, note`.
- 의도적으로 넣은 반례:
  - **G1 vs G2**: 같은 "화재"지만 다른 날짜·다른 지역(자동 SAME이면 오류)
  - **G4 vs G3**: 같은 기업의 2분기/3분기 실적(자동 SAME이면 오류)
  - **후속 보도**: 같은 사건의 원인 조사/피해 집계/지원 검토(SAME이어야 함)
  - **묶음 기사 2건**: 어떤 이슈에도 자동 연결 금지(REVIEW여야 함)
  - **모호 2건(E16 칼럼, E19 후속 정책)**: 사람도 갈리는 경우 → REVIEW가 허용되고 오류로 세지 않음
- 이 세트는 측정 도구입니다. 수정하면 이전 결과와 비교할 수 없으니 바꾸지 말고 `issue-eval-v2.json`을 새로 만드세요(`EvalDatasetTest`가 우발적 변경을 막음).

## 실행
`EvalRunner`가 발행시각 순으로 한 건씩 운영과 같은 규칙으로 처리합니다: 후보 없음→NEW, 묶음→REVIEW, 그 외 LLM 판단→`DecisionPolicy`(강등 규칙 포함). 결과를 메모리 이슈에 적용하며(NEW=ACTIVE 이슈 생성, SAME=기존 이슈에 추가, REVIEW=후보에서 제외되는 임시 이슈) 후보는 "ACTIVE 이슈 중 최근 갱신 N개"입니다(임베딩 검색 재현율은 별도 평가 필요: OPEN ITEM).

```bash
cd backend
mvn -Dtest=EvalLlmIT -Deval.run=true -Dspring.profiles.active=test -Dapp.ai.provider=<공급자> test
# 묶음 기사 판별 + 예측값을 쓴 분류까지 (호출이 사례당 1번 더 늘어남)
mvn -Dtest=EvalLlmIT -Deval.run=true -Deval.analysis=true -Dspring.profiles.active=test -Dapp.ai.provider=<공급자> test
```
`stub` 제공자로 돌리면 하네스가 동작하는지만 확인됩니다(스텁은 모델이 아님). 출력 예: `N=27 precision=… recall=… wrongAutoSameRate=… reviewRate=… adminEditRate=… errors={…}` 와 사례별 결과.

## 지표 정의 (`EvalMetrics`, 단위 테스트로 손계산 검증됨)
| 지표 | 정의 |
|---|---|
**2026-10-14 수정:** precision·recall과 오류 분류는 **명확한 사례(모호 표시 없음)만**으로 계산한다. 예전에는 recall 분자에 모호 사례가 들어가 1을 넘을 수 있었다(v2에서 1.077). 모호 사례는 결정 분포만 따로 보고한다.

| 지표 | 정의 |
|---|---|
| precision | 명확한 사례의 자동 SAME_ISSUE 중 정답 이슈에 연결된 수 / 명확한 사례의 자동 SAME_ISSUE 수 |
| recall | 명확한 SAME 정답 중 정답 이슈에 자동 연결된 수 / 명확한 SAME 정답 수 (분자는 분모의 부분집합) |
| SAME 정답 분해 | 자동 연결 성공(linked) + 다른 이슈에 자동 연결(wrongIssue) + NEW로 분리(splitAsNew = 병합 누락) + REVIEW 보류(heldForReview) = SAME 정답 수. 보류 중 같은 사건의 검수 대기 이슈에 붙은 것은 heldWithSameEvent |
| 모호 사례 | 건수와 자동 SAME / 자동 NEW / REVIEW 분포만 보고 |
| wrongAutoSameRate | 명확한 사례의 잘못된 자동 SAME_ISSUE 건수 / 전체 건수 — 가장 비싼 오류(이슈 오염) |
| reviewRate | REVIEW 건수 / 전체 — 사람 검수 부담 |
| adminEditRate | 명확한 사례의 잘못된 자동 결정 / 명확한 사례의 자동 결정 |
| errorTypes | `FALSE_MERGE`(자동 SAME이 다른 이슈/첫 보도에 붙음), `MISSED_MERGE`(같은 사건인데 자동 NEW), `BUNDLE_NOT_REVIEWED`, `REVIEW_COULD_BE_SAME/NEW`(명확한 답이 있었는데 REVIEW: 오류는 아니지만 자동화 손실), `HELD_WITH_OTHER_EVENT`(다른 사건의 검수 대기 이슈에 보류 연결), `INVALID_LLM_OUTPUT`, `GUARD_DOWNGRADE`(정책이 LLM 판단을 뒤집음) |

평가 하네스는 운영과 같이 검수 대기(REVIEW) 이슈도 후보로 제시하고, 거기에 맞으면 보류 연결(REVIEW)로 센다(묶음 기사로 생긴 검수 대기 이슈는 제외). 과거 로그는 `EvalLogRecompute`로 유료 호출 없이 재계산할 수 있다.

분모가 0이면 `n/a`(null)입니다.

## 데이터셋이 변별력이 있는지 확인한 방법
같은 세트를 단순 단어 겹침 판단기로 돌려 보면(작성 중 임시 스크립트) 같은 기업의 다른 분기 실적(E09/E10→G4)이 잘못 병합됩니다. 즉 반례가 실제로 오류를 유발합니다. 이 스크립트는 저장소에 포함하지 않았고, 수치는 기준선으로 쓰지 않습니다.

## 운영 데이터로 같은 지표 보기
운영에서는 `classification_run`(후보·원판단·적용 여부)과 `issue_article.manually_corrected`/`admin_audit_log`가 쌓입니다. 관리자가 병합/이동/분리한 건수를 자동 적용 건수로 나누면 실제 `adminEditRate`를 얻을 수 있습니다(전용 리포트 화면은 Phase 1 범위 밖).

## 합격 기준 초안 (2026-10-12, **미확정 — 사용자 결정 필요**)

### v1 세트의 구성 (발행시각 순 처리 기준으로 계산)
| 정답 | 건수 | 비고 |
|---|---|---|
| SAME (기존 이슈와 같은 사건) | 13 | recall의 분모. 1건 놓칠 때마다 약 7.7%p |
| NEW (첫 보도) | 10 | 이 중 강한 반례 2건: E09(G4와 다른 분기 실적), E05(G1과 다른 화재) |
| 묶음 기사 | 2 | E23, E24 |
| 모호 | 2 | E16, E19 (REVIEW 허용) |

- 후보는 "최근 갱신 ACTIVE 이슈 5개"로 단순화되어 있지만, 완벽한 판단기를 가정해 시뮬레이션하면 후보 목록에서
  정답 이슈가 빠지는 사례는 0건이다. 즉 13/13 재현율이 원리상 가능하고, 놓친 것은 모델·가드 탓이다.
- 표본이 작으므로 기준은 비율보다 **건수**로 정한다.

### 제안
| 구분 | 기준 | 이유 |
|---|---|---|
| 필수 | 오병합(`FALSE_MERGE`) **0건**, 즉 precision 1.0 | 오병합이 가장 비싼 오류. 특히 E09·E05 반례를 자동 SAME으로 붙이면 즉시 불합격 |
| 필수 | `INVALID_LLM_OUTPUT` 1건 이하 | 스키마 검증 실패가 잦으면 운영에서 REVIEW가 쌓임 |
| 목표 | recall **10/13 이상**(≈0.77) | 놓친 SAME은 오류가 아니라 새 이슈가 생기는 것이고 관리자 병합으로 복구 가능. 가드(SAME 신뢰도 0.85)가 보수적이므로 일부 손실을 허용 |
| 목표 | REVIEW **8건 이하**(≤30%) | 묶음 2 + 모호 2 = 설계상 4건은 REVIEW가 정상. 그 외 추가 REVIEW는 4건까지 |
| 반복성 | 같은 설정으로 **3회** 실행해 필수 기준은 3회 모두, 목표 기준은 중앙값으로 판정 | temperature 0이어도 응답이 매번 같다는 보장이 없음 |

미달 시 조정 순서: 오병합이 있으면 프롬프트·SAME 임계값을 올리는 쪽으로만 조정(내리지 않음).
recall만 낮으면 `GUARD_DOWNGRADE` 사례의 신뢰도 분포를 보고 SAME 임계값 조정을 검토한다.
임계값을 바꾸면 3회 측정을 다시 한다.

### 이 세트가 재지 않는 것
- **묶음 기사 판별:** 기본 실행은 정답 라벨의 `multiEvent`를 그대로 쓰므로 `BUNDLE_NOT_REVIEWED`는 항상 0이다.
  **2026-10-13 추가:** `-Deval.analysis=true`를 붙이면 운영과 같은 기사 분석 프롬프트(`ArticleAnalysisService.promptVariables`)로
  27건을 분석해 `multiEvent`를 측정하고(묶음 맞춤/놓침/오경보/분석 실패), 그 예측값으로 분류까지 다시 돌린다.
  놓친 묶음은 판단 모델로 가서 `BUNDLE_NOT_REVIEWED`로, 오경보는 `REVIEW_COULD_BE_*`로 잡힌다. 세트에 본문이 없어
  요약과 핵심 사실을 본문 대신 넣으므로 실제 기사보다 정보가 적다(결과는 하한선). 묶음이 2건뿐이라 놓침 1건이 50%p다.
- **임베딩 후보 검색 재현율:** 위의 단순화 때문에 측정하지 않는다(기존 OPEN ITEM).

### 실행 시 참고
`EvalLlmIT`는 `@SpringBootTest`라 테스트 DB가 필요하다. `DB_PASSWORD`(기본값 없음)와 `TEST_DB_URL`,
실제 공급자일 때 `OPENAI_API_KEY`를 함께 지정한다.
