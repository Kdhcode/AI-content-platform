## 1. 카테고리 분류

**원인.** `article-analysis/v1` 프롬프트는 "허용된 값 중 하나만 고른다"는 규칙만 있고 값별 정의가 없었다. 허용 값 목록은
스키마로 전달되지만 기준이 없어, 모델이 해외 기사·문화 기사를 `OTHER`로, 사건 기사를 `LIFE`로 보내는 경우가 많았다.
`60b89f6`에서 허용 목록 밖 값을 내 스키마 검증에 실패한 1회도 같은 원인으로 본다.

**수정.** `prompts/article-analysis/v2`를 추가하고 기본값을 v2로 바꿨다(`app.prompts.article-analysis-version`).
v1 폴더는 그대로 둔다(버전 폴더 불변 규칙). v2는 v1과 **스키마·사용자 템플릿이 같고** 시스템 지시만 다르다.
- 9개 카테고리마다 정의를 적고, 언론사나 소스 제공 카테고리가 아니라 사건 내용으로 판단하게 했다.
- 해외 사건·외국 정치는 `WORLD`, 한국의 사건·사고·범죄·재판은 `SOCIETY`, `LIFE`는 사건이 아닌 생활 정보로 한정, `OTHER`는 마지막 선택.
- 특정 기사·언론사 이름은 넣지 않았다. `PromptFilesTest`가 스키마의 모든 값에 정의가 있는지 검사한다.

**검증.** `60b89f6`의 실제 기사 중 v1이 틀린 14건과 맞은 6건을 골라, 기대 카테고리를 **실행 전에** 적어 두고 v2로 다시 분석했다.
v1 결과는 같은 날(2026-10-14) 오전 `60b89f6` 실행에서 저장된 값이다.

| | v1 (2026-10-14 오전) | v2 1차 | v2 2차 (최종) |
|---|---|---|---|
| v1 오분류 14건 | 0/14 | 11/14 | **13/14** |
| v1 정상 6건 | 6/6 | 6/6 | **6/6** |
| 합계 | 6/20 | 17/20 | **19/20** |

- 1차에서 틀린 3건: 뉴욕 센트럴파크 마차 폐지(→ POLITICS), 영국 MI5 경고(→ POLITICS), 은평구 금성당제(→ OTHER).
  외국 정치를 `POLITICS`로 보낸 2건 때문에 `POLITICS` 정의에 "외국의 정치·의회·지방정부·정보기관 소식은 WORLD"를 덧붙이고,

- **한계:** 같은 20건으로 프롬프트를 고치고 다시 쟀으므로 과적합 가능성이 있다. 새 기사로 확인하지 않았다.

## 2. RSS 분석 입력 정리

**문제.** SBS RSS 본문 앞뒤에 이용 조건·앱 안내 문구가 붙어 AI 입력에 들어갔다. 뉴시스는 끝에 "◎슬로건 + 기자 이메일"이 붙는다.

**수정.** `news/AnalysisInputCleaner`를 추가하고 `ArticleAnalysisService.promptVariables`에서 **AI에 보내는 사본만** 정리한다.
`news_article.analysis_text`에 저장된 원문(이용 조건 문구 포함)은 바꾸지 않는다.
- 지우는 것: 저작권 표시(ⓒ/©)가 붙은 재배포 금지 문구, 피드 이용 조건 문장, "▶ … 다운로드/확인하기/영상 시청/바로가기/구독" 같은 짧은 링크 문구, 이메일이 든 끝 서명, 그 밖의 이메일 주소.
- 언론사 이름 규칙은 없다. 재배포 금지 문구는 ⓒ/© 표시가 있거나 피드 자체를 말할 때만 지워, 불법 복제를 보도하는 기사 문장은 남는다(테스트로 확인).
- 정리 후 본문이 비면 기존과 같이 "(본문 없음 - 제목만 사용)"을 보낸다. 길이 제한(8,000자)은 정리 후 적용한다.
- **입력 정리는 콘텐츠 이용 허가와 별개다.** 정리했다고 해서 SBS 등 각 사의 RSS 이용 조건이 해소되지 않는다(OPEN_ITEMS #1).

**검증.** 실제 기사 35건에 정리기를 적용(`CleanerRealDataReport`, AI 호출 없음). 15건이 바뀌었다(SBS 10, 뉴시스 5).
지워진 조각을 모두 사람이 확인했고 전부 이용 조건·앱 안내·링크 문구·서명이었다. 기사 문장이 지워진 경우는 없었다.
나머지 20건(연합뉴스·동아·경향·BBC)은 바뀌지 않았다. 정리 후 남은 단어가 모두 원문에 있는지도 테스트가 확인한다.

## 4. 이슈 분류 평가 (대표 세트 27건, 실제 OpenAI)

`EvalLlmIT#printsMetricsForTheFixedSet`, 판단 프롬프트 `issue-classifier/v1`, 운영 임계값 그대로(SAME 0.85, NEW 0.70). 1회 실행.
평가 세트는 가상 기사이고, 정답은 "같은 사건 그룹"(`eventGroup`)과 묶음·모호 표시다. SAME/NEW 정답은 발행 순서와 그룹에서 계산된다.

| 지표 | 결과 | 합격 기준 초안 (`docs/EVALUATION.md`, 미확정) |
|---|---|---|
| 오병합 `FALSE_MERGE` | **1건 (E09)** | 0건 — **미달** |
| 스키마 실패 | 0건 | 1건 이하 — 충족 |
| SAME 재현율 (모호 제외) | 11/13 | 10/13 이상 — 충족 |
| REVIEW | 3건 (E08, 묶음 E23·E24) | 8건 이하 — 충족 |
| 반복성 | 1회만 실행 | 3회 — **미실행** |

전체 지표: precision 0.923, recall 0.923, 자동 오병합률 0.037, REVIEW 비율 0.111.

판정별로 나온 것: 후보가 있는 상황에서 NEW_ISSUE(LLM) 10건, SAME_ISSUE 13건, 후보 없음 NEW 1건, REVIEW 1건(LLM)과 묶음 REVIEW 2건이 모두 나왔다.

오분류:
- **E09 → 오병합.** 같은 회사의 **다른 분기(3분기) 실적**을 2분기 실적 이슈(G4)에 자동으로 붙였다. 세트에 일부러 넣은 반례이고, 초안의 필수 기준 위반이다.
- **E10 → 놓친 병합.** 같은 3분기 실적 후속 기사(G3)인데 NEW_ISSUE로 판단했다. E09가 G4에 붙어 G3 이슈가 없었던 영향으로 보인다.
- **E08 → REVIEW.** 같은 2분기 실적 후속 기사(G4)인데 신뢰도가 기준에 못 미쳐 REVIEW가 됐다(관리자 확인으로 복구 가능).
- E16(모호, 칼럼)은 NEW_ISSUE, E19(모호)는 SAME — 둘 다 허용 범위.

다음 조치 제안(이번에 하지 않음): 분류 프롬프트에 "같은 회사라도 다른 기간의 실적·발표는 다른 사건" 규칙을 넣은 `issue-classifier/v2`를
만들고 3회 측정. 초안 규칙대로 오병합이 있으면 임계값은 올리는 쪽으로만 조정한다.

## 7. 미검증·남은 문제

- **묶음 기사 판별(`eval.analysis`)**: 분석 27회 + 재판단 약 24회가 필요해 호출 상한(100) 안에 들어가지 않아 실행하지 않았다.
- **분류 평가 반복 측정**: 1회만 실행했다. 합격 기준 초안의 3회 반복은 미실행.
- **오병합 E09**: 미수정. 합격 기준 초안 기준으로 현재 분류 품질은 **불합격**이다.
- **카테고리**: 새 기사로 재확인하지 않았다. 금성당제 1건은 여전히 OTHER.
- **실제 파이프라인 재실행**: 새 기사를 수집해 v2 프롬프트로 전체 흐름(수집→분석→임베딩→분류)을 다시 돌리지는 않았다. 이번 검증은 저장된 기사 재분석과 평가 하네스로 했다.
- **청구액 대조**: OpenAI 사용량 화면의 실제 청구액과 추정 비용을 비교하지 않았다.

## 8. 2차 작업: 오병합 대응과 추가 검증 (2026-10-14 오후)

같은 날 오후, 1~7절의 남은 문제(오병합 E09, 반복 측정·묶음 판별·새 기사 처리 미실행)를 이어서 처리했다.
모델 `gpt-4o-mini`(응답 `gpt-4o-mini-2024-07-18`), `text-embedding-3-small`. 운영 임계값은 그대로(SAME 0.85, NEW 0.70).

### 8-1. 오병합·병합 누락 원인

| 사례 | 단계 | 근거 |
|---|---|---|
| E09 오병합 | **AI 판단** | v1 응답 이유에 "3분기 8% 증가"와 "2분기 12% 감소"를 모두 적고도 "같은 기업의 실적 발표이므로 같은 사건"이라며 SAME(0.9)을 냈다. v1 프롬프트에 "같은 기업의 다른 분기 실적은 반례"가 이미 있었는데도 따르지 않았다. 후보 생성은 정상(정답이 NEW라 맞는 후보가 없는 상황), 결과 적용은 정책대로(신뢰도 0.9 ≥ 0.85, 후보 안의 id) 적용됐다 |
| E10 병합 누락 | **결과 적용의 연쇄** | E10은 3분기 실적 후속 기사인데, 같은 3분기 첫 기사 E09가 2분기 이슈에 붙어 3분기 이슈가 생기지 않았다. 후보에는 2분기 이슈만 있었고 모델은 "다른 분기"라며 NEW를 냈다(그 자체로는 맞는 판단) |

평가 하네스의 후보 생성은 "최근 갱신 ACTIVE 이슈 5개"로 단순화되어 있다(운영은 임베딩 유사도 검색). 이번 원인 분석 범위에서는 후보 생성이 오류 원인이 아니었다.

### 8-2. 분류 프롬프트 v2·v3

- **v2**(`issue-classifier/v2`, v1과 스키마·템플릿 동일): "같은 사건"을 대상·행위·대상 기간·장소로 정의하고, 기간·장소·행위가 다르면 별개 사건, 발행일만 다른 후속 보도는 같은 사건, 근거 부족·충돌은 REVIEW로 정리.
  → 평가 3회 모두 **E09 오병합이 그대로** 났다. 모델이 "서로 다른 분기이지만 같은 회사의 실적 발표"라고 쓰며 SAME을 골랐다. 지시문만으로는 막지 못했다.
- **v3**(`issue-classifier/v3`, 스키마 `issue-classifier.v3`): v2 지시문에 **항목별 비교 `comparison`(actor/action/period/place: SAME·DIFFERENT·UNKNOWN·NOT_APPLICABLE)** 을 필수로 추가.
  `DecisionPolicy`가 SAME_ISSUE인데 모델 자신의 비교에 DIFFERENT가 있거나 actor·action이 UNKNOWN이면 자동 적용하지 않고 REVIEW로 강등한다(`GUARD_DOWNGRADE`).
  - v3 초안에서는 모델이 후속 보도의 **기사 날짜**를 period DIFFERENT로, 후속 **세부 행위**를 action DIFFERENT로 표시해 정상 후속 기사까지 막혔다(재현율 8~9/13).
  - 최종 v3는 비교 대상을 "기사가 다루는 원래 사건"으로, period를 "내용이 대상으로 하는 기간(실적의 분기 등). 발생일·발행일 차이는 아님"으로 정의했다.
- 특정 평가 ID·기사 제목·회사명은 넣지 않았다. v1·v2는 그대로 보존했다. 분류 프롬프트 기본값을 **v3**로 바꿨다(`app.prompts.issue-classifier-version`).
- 프롬프트 수정은 v2 → v3 초안 → v3 최종, 3회(협업 규칙의 최대 반복 횟수)로 멈췄다.

### 8-3. 대표 세트 27건 반복 평가

계산 기준(`EvalMetrics`): precision = 맞은 자동 SAME / 전체 자동 SAME. 도구의 recall = 맞은 자동 SAME / 모호하지 않은 SAME 정답(13건)인데,
**분자에 모호 사례(E16·E19)의 SAME도 들어가** 1을 넘을 수 있다. 그래서 합격 기준 판정에는 모호 사례를 뺀 "SAME 정답 13건 중 맞힌 건수"를 따로 셌다.
각 회차는 빈 이슈 목록에서 시작한다(`EvalRunner`가 실행마다 새 상태를 만든다).

| 프롬프트 | 회차 | 오병합 | 병합 누락 | REVIEW | 스키마 실패 | precision | SAME 정답 13건 중 |
|---|---|---|---|---|---|---|---|
| v1 (오전, **1회만**) | 1 | 1 (E09) | 1 (E10) | 3 | 0 | 0.923 | 11 |
| v2 | 1·2·3 (세 회 동일) | 1 (E09) | 1 (E10) | 2 (묶음 2) | 0 | 0.933 | 12 |
| v3 초안 | 1 / 2 / 3 | 0 / 0 / 0 | 3 / 3 / 3 | 6 / 5 / 6 | 0 (재시도 1회로 복구) | 1.000 | 8 / 9 / 8 |
| **v3 최종** | 1 / 2 / 3 | **0 / 0 / 0** | 3 / 1 / 3 | 3 / 4 / 3 | 0 | **1.000** | **10 / 11 / 10** |
| v3 최종 (8-4의 연결 실행) | 4번째 | 0 | 2 | 6 | 0 | 1.000 | 8 |

- v1과의 비교는 v1이 **1회 측정**이라는 한계가 있다.
- v3 최종에서 E09는 3회 모두 GUARD_DOWNGRADE로 REVIEW가 됐다(오병합 → 관리자 확인). 자동으로 NEW가 된 것은 아니다.
- 병합 누락: E10은 v3 전 회차에서 놓쳤다. E09가 REVIEW 임시 이슈가 되고, REVIEW 이슈는 후보에서 빠지므로(운영 정책과 같음) 3분기 이슈가 없어서다. 그 밖에 E08·E15·E11·E25가 회차에 따라 NEW나 REVIEW로 빠졌다.
- REVIEW가 늘어서 오병합만 줄어든 것인가: v3 최종의 REVIEW는 3~4건(묶음 2 포함)으로 v1(3건)과 비슷하다. 대신 **재현율이 회차마다 10~11/13, 연결 실행에서는 8/13으로 흔들린다.** 오병합을 막은 대가로 같은 사건을 놓치는 경우가 생겼다.
- 회귀: 정답이 NEW인 정상 사례(E01·E05·E12·E14·E17·E20·E21·E22)는 전 회차에서 NEW를 유지했다. 모호 사례 E16·E19는 SAME 또는 NEW로 허용 범위 안이었다.

**합격 기준 초안**(`docs/EVALUATION.md`, 사용자 확정 전) 대비, v3 최종 3회 기준:

| 기준 | 결과 | 판정 |
|---|---|---|
| 필수: 오병합 0건(3회 모두) | 0 / 0 / 0 | 충족 |
| 필수: 스키마 실패 1건 이하 | 0 | 충족 |
| 목표: 재현율 10/13 이상(중앙값) | 10 / 11 / 10 → 중앙값 10 | 충족(경계값) |

단, 4번째 실행(8-4)에서는 재현율 8/13으로 목표에 못 미쳤다. 기준을 결과에 맞춰 바꾸지 않았다. 표본 27건과 회차 간 흔들림을 고려하면 "안정적으로 충족"이라고 보기는 어렵다.

기준 `e6bde0d`. 분류 프롬프트 v3와 운영 임계값(SAME 0.85, NEW 0.70)은 그대로 두고 코드 변경의 효과만 확인했다.

### 9-1. 평가 지표 계산 수정 (`EvalMetrics`)

**문제.** 도구의 recall은 분자(맞은 자동 SAME)에 모호 사례를 넣고 분모(SAME 정답)에서는 뺐다. 그래서 v2 평가에서 recall=1.077이 찍혔다.

**수정.** 모든 비율을 "명확한 사례"(모호 표시가 없는 25건)만으로 계산하고, 모호 사례는 따로 보고한다.

| 지표 | 정의 |
|---|---|
| precision | 명확한 사례 중 자동 SAME이 맞은 수 / 명확한 사례 중 자동 SAME 수 |
| recall | 명확한 SAME 정답 중 맞는 이슈에 자동 연결된 수 / 명확한 SAME 정답 수 (분자는 항상 분모의 부분집합) |
| SAME 정답 분해 | 자동 연결 성공 + 다른 이슈에 연결 + NEW로 잘못 분리(병합 누락) + REVIEW 보류 = SAME 정답 수. REVIEW 보류 중 "같은 사건의 검수 대기 이슈에 붙은 것"은 따로 셈 |
| 모호 사례 | 자동 SAME / 자동 NEW / REVIEW 건수만 보고(맞음·틀림 없음) |
| reviewRate, wrongAutoSameRate | 전체 27건 기준(변경 없음) |
| adminEditRate | 명확한 자동 판단 중 틀린 비율 |

값을 0~1로 잘라내지 않았다. 회귀 테스트 `ambiguousHitsNoLongerInflateRecall`가 v2와 같은 모양(명확한 SAME 13건 중 12건 연결 + 모호 2건 연결)에서 예전 값 14/13 대신 12/13이 나오는지 확인한다.

**기존 결과 재계산(유료 호출 없음).** 로컬에 남은 평가 로그 11개(`CaseResult` 줄)로 `EvalLogRecompute`가 다시 계산했다.

| 실행 | 예전 출력 recall | 수정 recall | precision | 연결 성공 | 다른 이슈 | NEW로 분리 | REVIEW 보류 | REVIEW 전체 |
|---|---|---|---|---|---|---|---|---|
| v1 (오전 1회) | 0.923 | **0.846 (11/13)** | 0.917 (11/12) | 11 | 0 | 1 | 1 | 3 |
| v2 r1·r2·r3 | 1.077 | **0.923 (12/13)** | 0.923 (12/13) | 12 | 0 | 1 | 0 | 2 |
| v3 초안 r1/r2/r3 | 0.615/0.692/0.615 | 0.538/0.615/0.538 | 1.000 | 7/8/7 | 0 | 3/3/3 | 3/2/3 | 6/5/6 |
| v3 최종 r1/r2/r3 | 0.923/0.923/0.923 | **0.769/0.846/0.769** | 1.000 | 10/11/10 | 0 | 3/1/3 | 0/1/0 | 3/4/3 |
| v3 최종 연결 실행 | 0.692 | 0.615 (8/13) | 1.000 | 8 | 0 | 2 | 3 | 6 |

v1의 오병합(E09)은 정답이 NEW인 사례라 "SAME 정답 분해"가 아니라 FALSE_MERGE로만 잡힌다. 8절 표의 "SAME 13건 중" 숫자는 수작업으로 센 값이었고 재계산 결과와 같다.

### 9-2. 검수 대기 이슈의 후속 기사

**기존 흐름.** REVIEW 판단이 나면 그 기사로 검수 대기(REVIEW) 이슈를 새로 만든다. 후보 검색은 ACTIVE 이슈만 대상으로 해, 검수 대기 이슈에는 후속 기사가 붙을 수 없었다(E10). 관리자가 REVIEW → ACTIVE로 확정하면 소속 기사가 모두 CLASSIFIED가 되고, 병합·분리·이동·제외도 기존대로 할 수 있다.

**선택한 방식: 검수 대기 이슈를 후보로 제시하고, 같은 사건이면 그 이슈에 "보류 연결"한다.** 기존 구조(검수 대기 이슈, 관리자 확정·병합·분리)를 그대로 쓰는 최소 변경이다.
- 후보 검색 대상 기본값을 `ACTIVE, REVIEW`로 바꿨다(`app.classifier.candidate-issue-statuses`). 단, 묶음 기사(MULTI_EVENT)로 생긴 검수 대기 이슈는 여러 사건을 담으므로 후보에서 뺀다.
- 분류는 그대로 v3 + `DecisionPolicy`(신뢰도·항목별 비교). 이를 통과한 SAME_ISSUE가 검수 대기 이슈를 가리키면 적용 단계에서 행 잠금으로 상태를 다시 확인하고, 기사를 그 이슈에 `LLM_REVIEW`로 연결하며 기사 상태는 REVIEW로 둔다. 실행 기록은 decision REVIEW, raw SAME_ISSUE, matched/applied = 그 이슈.
- **자동 처리의 경계:** 검수 대기 이슈를 ACTIVE로 바꾸지 않는다. 기사를 CLASSIFIED로 만들지 않는다. 판단은 AI가 하지만 확정은 관리자가 한다.
- **관리자 처리:** 이슈 확정(ACTIVE)이면 묶인 기사 전부 CLASSIFIED, 잘못 붙었으면 분리(split)로 떼어낸다(테스트로 확인). 병합·제외도 기존 기능 그대로.
- **반복 방지:** 이미 연결된 기사를 다시 분류하면 실행 기록만 남고 연결은 바뀌지 않는다(기존 규칙, 테스트로 확인). 관리자 확정 뒤 재분류 작업을 만들지 않으므로 추가 유료 호출이나 재시도 반복이 없다.
- **공개 노출:** 공개 뉴스룸 API(`/api/public`)는 이 브랜치에 없다. `feature/public-news`의 공개 API는 ACTIVE·CLOSED 이슈만 보여 주므로 검수 대기 이슈와 거기 보류 연결된 기사는 나오지 않는 구조지만, **이 브랜치에서 공개 API 회귀 테스트는 실행할 수 없어 미검증**이다(뉴스룸 브랜치를 병합하지 않았다).
- 선택하지 않은 방식: "검수 완료 후 관련 기사 재검토"는 관리자 확정 시점에 재분류 작업과 유료 호출이 생기고, 그 사이 후속 기사가 흩어진 상태가 유지된다.

### 10-1. 기간 규칙 (`PeriodGuard`, `DecisionPolicy.applyPeriodGuard`)

9-2의 E09 재발은 모델이 기간을 스스로 잘못 표시한 경우였다. 그래서 모델의 표시와 별도로 코드가 기간을 비교한다.

- **적용 범위:** 기사나 후보 중 한쪽에 실적·통계 단어(실적, 영업이익, 매출, 고용동향, 취업자, 물가, 수출, 통계, 지표 등)와 기간 표기가 함께 있을 때만 적용한다. 그 밖의 사건(화재, 예산 발표 등)은 `NOT_APPLICABLE`로 두고 판단을 바꾸지 않는다.
- **기간 종류:** 분기(“2026년 3분기”), 분기 범위(“1~3분기”), 반기, 월(분기·반기 표기가 없을 때만), 연간 실적. **날짜(“10월 20일”, “9월 말”)와 연도만 있는 표기(“2027년 예산”)는 기간으로 보지 않는다.**
- **대상 기간과 비교 기간 구분:** “2분기 대비”, “전년 동기보다”, “지난해 3분기” 같은 표기는 비교 기간으로 빼고, 남은 기간을 대상 기간으로 본다. 기간이 여러 번 나온다는 이유만으로 검수로 보내지 않는다.
- **판정:**
  - `CONFLICT`: 대상 기간이 다르거나, 양쪽에 연도가 있는데 연도가 다르다.
  - `UNCLEAR`: 대상 기간이 없거나, 둘 이상이거나, 단위가 달라 비교할 수 없다.
  - `CONSISTENT`: 대상 기간이 같다. 한쪽에 연도가 없으면 “연도 미확인이라 같은 사건의 근거로 쓰지 않음”을 남긴다.
  - 규칙은 SAME을 막거나 그대로 둘 뿐, SAME을 새로 만들지 않는다. 그래서 연도가 없는 같은 분기가 SAME의 근거가 되지 않는다.
- **우선순위:** AI가 SAME_ISSUE를 냈어도 `CONFLICT`나 `UNCLEAR`이면 REVIEW(`GUARD_DOWNGRADE`)로 바꾼다. 사유는 “기간 규칙: …”으로 시작하고, 추출한 대상 기간·근거 문자열과 원래 AI 사유를 함께 남긴다. `CONSISTENT`이면 판단은 그대로 두고 사유에 근거만 덧붙인다.
- **위치:** 운영 분류(`IssueClassificationService`)와 평가 실행기(`EvalRunner`)가 같은 함수를 쓴다. 비교하는 텍스트는 기사의 제목·요약·핵심 사실과 후보 이슈의 제목·요약·핵심 사실이다.
- **테스트:**
  - `PeriodGuardTest` 11개: 다른 분기, 같은 분기 후속, 비교 기간, 연도 없는 분기, 다른 연도, 월별 통계, 날짜·연도 무시, 불명확, 범위·연간, 반기, 모델보다 규칙 우선.
  - 회귀 테스트 `EvalRunnerTest.periodRuleBlocksTheMergeTheModelsOwnComparisonMissed`: v1의 실제 E07~E09 문장에 AI가 SAME(기간 NOT_APPLICABLE)을 내는 상황을 넣었다. E09는 REVIEW가 되고, 같은 분기 후속인 E08은 SAME으로 남는다.
- **한계:** 같은 분기·다른 회사(v2의 V06과 H2)는 규칙이 막지 않으며, 주체 구분은 AI(v3 actor 비교)에 맡긴다. v2의 모든 기사 쌍을 오프라인(무료)으로 돌린 결과, 같은 사건 쌍이 규칙에 막힌 경우는 0건이었다.

### 10-4. 검수 부담 기록 방식

실제 유입 데이터가 없으므로 **하루 검수 건수는 추정하지 않는다.** 표본 기준 검수 비율만 기록한다: v2 0.059~0.294, v1 0.185. 평가 세트는 일부러 어려운 사례를 모은 것이라 이 비율이 운영 비율은 아니다. 9-3의 실제 다매체 8건에서는 REVIEW가 0건이었다.

관리자 처리 시간은 10-5의 브라우저 확인에서 쟀다: 분리 1건과 확정 1건에 약 12.4초, 병합 1건에 약 13.8초. **사람이 아니라 자동화 도구가 조작한 시간**이라 사람이 판단하는 시간은 들어 있지 않다.

### 10-5. 관리자 검수 화면

이슈 상세 API의 기사 항목에 분류 실행 기록(`classification_run`)을 붙였다:
- `runMethod`, `runDecision`: 이 기사를 연결한 분류 실행의 방식과 판단.
- `heldWithPendingIssue`: 검수 대기 이슈에 보류 연결된 후속 기사인지 여부.
- `candidates`: AI가 비교한 후보 이슈(id, 상태, 제목, 유사도).

화면(`/issues/{id}`):
- REVIEW 이슈 위에 “검수 대기” 안내를 띄운다. 확정·분리·병합이 각각 무엇을 하는지와 검수 사유별 건수를 보여 준다.
- 기사 표에 “검수 사유”를 표시한다: 보류 연결(같은 사건 판단), 기간 규칙, 묶음 기사, AI 출력 오류, AI 비교 모순, 신뢰도 부족, 대상 이슈 상태 변경, AI가 검수 요청. 원문 사유도 그대로 보여 준다.
- “비교 후보” 열에 후보 이슈 링크, 상태(REVIEW 등), 유사도, 제목을 보여 준다.
- 버튼 이름을 “같은 사건으로 확정(ACTIVE)”과 “선택한 기사 별도 사건으로 분리”로 바꿨다. 동작은 기존 API 그대로다.

**브라우저 확인(내장 브라우저, 2026-10-14).**

- 계정: 테스트용 관리자 계정을 새로 만들어 썼다.
- 사용자 화면 서버(8090/3090)와 기존 DB는 건드리지 않았다.

### 10-7. 남은 문제와 미검증

- 이번 6회의 실제 모델 실행에서는 기간 규칙이 단독으로 오병합을 막은 사례가 없었다(테스트로만 확인).
- 같은 분기·다른 회사의 구분, 날짜가 다른 일반 사건의 구분은 AI에 의존한다.
- 병합 누락 V15와 E08이 남았다. v2는 규칙을 만든 사람이 같은 날 만든 세트다.
- 검수 사유는 저장된 사유 문자열의 앞부분과 실행 방식으로 분류한다. 사유 문구를 바꾸면 화면 분류도 함께 고쳐야 한다.
- 공개 API에서 검수 대기·보류 연결 기사가 숨겨지는지는 통합 브랜치에서 확인한다.
